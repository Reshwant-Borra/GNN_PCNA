## The deepest one — empirically proven, beyond the static audit

The audit flagged the MD analysis ran on unaligned coordinates. Running the actual 1AXC 25 ns trajectory proved the true root cause is worse and more specific:

- The analysis **superposed the whole PCNA trimer**, folding large inter-subunit motion into every metric → backbone RMSD **27 Å** (the "corrupt" false-negative signature).
- **Per-chain** alignment gives **1.7 Å**, and the pocket's real dynamics appear (volume breathes ~430 Å³, mouth opens ~5.4 Å).
- PBC imaging (the audit's hypothesis) changes **nothing** here — each chain is already whole.

This is why `run_md_analysis.py` now aligns and measures **per chain**, and emits a 3-way verdict (`DYNAMICS` / `VALID_NEGATIVE` / `INVALID_ANALYSIS`) so a broken run can never again be read as "no dynamics."

**1. 🔴 CRITICAL — AlignTraj(in_memory=False) does not rewire the universe — RMSF (and everything after) runs on UNALIGNED coordinates**

- *Where:* compute_rmsf, lines 50-60 (align call line 54, RMSF line 59)  · *type:* `scientific-validity`
- *What goes wrong:* align.AlignTraj(u, ref, select='backbone', in_memory=False).run() streams the aligned frames to a separate on-disk trajectory (default 'rmsfit_*' file) and returns; it does NOT modify u.trajectory in place. The very next line, rms.RMSF(ca).run(step=stride), iterates the ORIGINAL, still-unaligned u. So RMSF is computed with global rigid-body translation/rotation of the whole trimer left in. The inline comment on lines 52-53 asserts the opposite ('all frames so RMSF ... doesn't double-skip'), which is exactly the documented MDAnalysis pitfall. Pocket vs background RMSF are both dominated by whole-ring tumbling, so their ratio (fold_change) is meaningless and the pocket looks like it has no distinctive dynamics.
- *Why it matters:* This is the single biggest reason 'the pocket has no dynamics': the reported per-residue RMSF is rigid-body motion, not internal flexibility. The apo-vs-background fold-change written to md_rmsf_1W60.json and md_apo_comparison.json, and compared against the ANM number (0.857), is scientifically invalid.
- *Fix:* Use in_memory=True so u is actually rewired: align.AlignTraj(u, ref, select='backbone', in_memory=True).run(); OR write to a file and reload that file as the universe before RMSF; OR pass the aligned trajectory into rms.RMSF. Verify by checking that ref-frame RMSD drops to ~0 after alignment. Also align on a stable core selection that excludes the AOH pocket residues to avoid circularity (see separate finding).
- *Note:* Primary fix: in_memory=True on AlignTraj so u is actually rewired (or reload the rmsfit_ output file as the universe before RMSF). Verify by checking ref-frame RMSD drops to ~0 post-alignment. Note the same unaligned-coordinate defect also invalidates compute_dccm (lines 84-88) since it iterates the same non-rewired u — worth fixing together. Additionally align on a stable core selection that excludes AOH pocket residues to avoid circularity, and require PBC unwrap/make_whole upstream before alignment.

**2. 🟠 HIGH — Pocket-volume convex hull is built from residues in ALL THREE chains — measures the whole ring, not the pocket**

- *Where:* compute_pocket_volume line 114 (mask by resid only) + call site line 220 (passes chain-agnostic AOH_GT)  · *type:* `scientific-validity`
- *What goes wrong:* mask = np.array([r in pocket_resids for r in resids]) matches Ca atoms by residue NUMBER only, and pocket_resids is AOH_GT — the chain-agnostic union (line 38). PCNA is a homotrimer, so every pocket residue number appears in chains A, B AND C. The selected Ca cloud is therefore spread across all three subunits and the ConvexHull spans the entire ~19,700 Å^3 ring. A hull over the whole trimer barely changes frame-to-frame regardless of how the A-B interface pocket breathes, so the volume time series is flat by construction — 'the pocket has no dynamics'. The AOH1996 pocket is a per-interface (A+B only, not C) cavity; a convex hull of Ca across three subunits cannot represent it.
- *Why it matters:* The core deliverable (md_pocket_volume.json) cannot show pocket opening/closing. It reports ring size, not cavity volume, so any conclusion about pocket breathing from MD is invalid.
- *Fix:* Match chain-specifically using segids and AOH_GT_BY_CHAIN, restrict to a single interface (chain A + chain B pocket residues only, exclude C), and compute volume per interface. Better: replace the Ca convex hull with a real cavity metric (fpocket/MDpocket per frame, or interface SASA / a pocket-lining-atom hull) since a convex hull of pocket-lining Ca overestimates and is insensitive to closure.
- *Note:* Fix direction is right but adjust the rationale to the real system: it is an A/B dimer, so the chain-agnostic mask merges chain A + chain B pocket residues (two subunits), not three; the hull measures dimer geometry, not a whole trimeric ring. Restrict to a single interface using segids + AOH_GT_BY_CHAIN (e.g. chain A pocket residues, or a defined A+B interface subset), and prefer a true cavity metric (interface SASA or fpocket/MDpocket per frame) over a Cα convex hull, which both overestimates and is insensitive to closure. Also apply chain-specific matching to the RMSF pocket_mask at line 170, which has the same defect.

**3. 🟠 HIGH — Pocket residue mask for RMSF is chain-agnostic — contaminates the pocket set with chain C and wrong cross-chain residues; AOH_GT_BY_CHAIN is never used**

- *Where:* main, line 170 (pocket_mask = [r in AOH_GT for r in resids]); AOH_GT built line 38  · *type:* `scientific-validity`
- *What goes wrong:* pocket_mask matches every residue whose NUMBER is in AOH_GT, ignoring chains/segids (which are captured on line 60 but never used). AOH_GT is the union of the chain-A and chain-B residue sets, so: (1) chain C residues with those numbers are wrongly flagged as pocket (the AOH1996 pocket exists only at the A-B interface, not chain C); (2) residues that belong to only one chain's pocket (e.g. 23 is in B but not A) get flagged in the other chain too. The per-chain dict AOH_GT_BY_CHAIN (lines 32-37) that would enable correct matching is defined but never referenced. This inflates the pocket-residue count (reported as aoh_pocket_residues in the summary) roughly 3x and mixes flexible/rigid environments, biasing pocket_rmsf and the fold-change.
- *Why it matters:* Wrong chain assignment is a direct scientific-correctness defect flagged as unacceptable for this project. The pocket-vs-background RMSF ratio and DCCM subset are computed over the wrong residue set.
- *Fix:* Build the mask with chain awareness: pocket_mask = np.array([ (resids[i] in AOH_GT_BY_CHAIN.get(chains[i], set())) for i in range(len(resids))]). Confirm segids actually carry chain IDs (A/B/C) for this topology; if the PDB loads chains into chainIDs not segids, select on the correct attribute.
- *Note:* The proposed fix (key on chains[i] from ca.segids) is correct in shape but has a load-bearing caveat: MDAnalysis often puts the PDB chainID column into the chainIDs attribute rather than segids (segids may default to 'SYSTEM' or blank for OpenMM/pdbfixer-written PDBs). Before shipping, verify which attribute actually carries 'A'/'B'/'C' for this topology and select on it (return ca.chainIDs if segids are empty); otherwise the corrected mask silently matches nothing and pocket_rmsf becomes None. Note the per-interface convex-hull volume issue is a separate but related defect that the same chain-aware fix only partially addresses.

**4. 🟠 HIGH — No PBC unwrap / make_whole before alignment — periodic wrapping produces huge RMSF, volume and DCCM artifacts**

- *Where:* main, universe load lines 159-164 and compute_rmsf/compute_dccm/compute_pocket_volume (no transformations added anywhere)  · *type:* `scientific-validity`
- *What goes wrong:* The trajectory is loaded and used directly; no MDAnalysis on-the-fly transformation (unwrap/make_whole, center, wrap) is ever applied. If the production DCD stored coordinates wrapped into the periodic box (the common OpenMM/Colab default), individual chains of the trimer — or atoms of a residue — can be split across box boundaries. Aligning and then computing RMSF, convex-hull volume, or DCCM on wrapped coordinates yields enormous spurious jumps (a residue teleporting a full box length) that swamp the real signal. Alignment must be performed AFTER unwrapping, not before.
- *Why it matters:* Wrapped frames make RMSF and pocket-volume time series noisy/invalid and can make the pocket look either frozen (dominated by one artifact) or randomly spiky. Standard MD-analysis correctness requirement.
- *Fix:* Add transformations right after building u: from MDAnalysis import transformations as trans; u.add_transformations(trans.unwrap(u.atoms), trans.center_in_box(protein, wrap=True)) (or at minimum trans.unwrap). Do this before AlignTraj and before any positions are read.
- *Note:* Add imaging before AlignTraj and before any positions are read. But the finding's literal one-liner trans.unwrap(u.atoms) is insufficient/broken as written: (1) a plain PDB topology in MDAnalysis carries no bonds, so unwrap raises NoDataError unless bonds are guessed first (u.atoms.guess_bonds() or Universe(..., guess_bonds=True)); (2) unwrap makes each chain whole but does not force two separately-wrapped chains into the same periodic image, so inter-chain box jumps can persist. A correct fix: guess bonds, then add_transformations(trans.unwrap(protein), trans.center_in_box(protein, wrap=False)) treating the whole protein as one compound so all subunits are reassembled and kept together, applied to u before AlignTraj and before compute_dccm/compute_pocket_volume read ca.positions. Note this finding is distinct from, and compounded by, the separate AlignTraj(in_memory=False) issue (alignment not rewiring u) and the chain-agnostic pocket-residue matching that pulls in chain C.

**5. 🟠 HIGH — DCCM is computed on unaligned coordinates — no alignment inside compute_dccm and u was never rewired**

- *Where:* compute_dccm, lines 63-94 (positions read at lines 77 and 85)  · *type:* `scientific-validity`
- *What goes wrong:* compute_dccm reads ca.positions directly with no superposition/alignment step. Rigid-body tumbling makes all residues appear strongly positively correlated, so the DCCM (and the pocket_internal DCCM printed on line 215 and compared to the ANM 0.0995) reflects whole-molecule motion, not internal correlated dynamics.
- *Why it matters:* DCCM is only meaningful after removing rigid-body motion. As written it produces an artifactually correlated matrix, invalidating the md_dccm_1W60.npy output and the ANM-vs-MD DCCM comparison.
- *Fix:* Ensure DCCM runs on the aligned trajectory: fix the alignment so u is rewired (in_memory=True), or align a fresh in-memory copy on a stable core (excluding pocket residues) at the top of compute_dccm before the two accumulation passes.
- *Note:* Align a fresh in-memory copy of the trajectory inside compute_dccm before both accumulation passes, superposing onto a STABLE core that EXCLUDES the pocket residues being measured (avoids circularity), e.g. align.AlignTraj(u_mem, ref, select="name CA and (backbone core selection)", in_memory=True).run(), then read positions from the rewired universe. Simply flipping in_memory=True in compute_rmsf is insufficient by itself because compute_dccm receives the original u passed from main; the alignment must be guaranteed within compute_dccm (or a rewired universe must be threaded through). Also apply PBC unwrap/make_whole before alignment so wrapped chains do not corrupt the superposition.

**11. 🟠 HIGH — Internal DCCM uses abs() — destroys sign, conflates correlated and anti-correlated motion**

**14. 🟡 MEDIUM — No PBC unwrap / make_whole before alignment or volume → wrapped chains cause huge RMSD/volume artifacts**
